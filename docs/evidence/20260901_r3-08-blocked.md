## Detection attempts and outputs (fresh runs in this task session)

### Probe 1 — Apple USB PnP device enumeration

```powershell
Get-PnpDevice -PresentOnly |
  Where-Object { $_.InstanceId -match 'VID_05AC' -or
                 $_.FriendlyName -match 'Apple|iPhone|iPad' }
(Get-PnpDevice -PresentOnly | Measure-Object).Count
```

Output: 6 present devices matched, all only via friendly name — Bluetooth
profile endpoints of a previously Bluetooth-paired iPhone (`Hands-Free HF`,
`Hands-Free HF Audio`, `Avrcp トランスポート` ×2, `A2DP SNK`, and one
`iPhone 17` Bluetooth entry; classes System / Bluetooth / MEDIA). **No device
matched `VID_05AC`** (no Apple USB device, no Apple Mobile Device USB driver).
Total present PnP devices: 294 (USB/PnP enumeration itself works — the filter
has something to enumerate, and finds no Apple USB attachment).

Interpretation: Bluetooth audio pairing only. A Bluetooth pairing provides no
usbmux/lockdown attachment for this runtime's transport. Friendly names are
product/profile labels, not device identifiers.

### Probe 2 — Apple services

```powershell
Get-Service | Where-Object { $_.Name -match 'Apple' -or
                             $_.DisplayName -match 'Apple|Mobile Device' }
```

Output: `NONE FOUND` — the classic `Apple Mobile Device Service` is not
installed. (The modern Microsoft Store **Apple Devices** app provides the
mobile-device support process instead; see Probe 5.)

### Probe 3 — Classic usbmuxd named pipe

```python
import os
print(os.path.exists(r"\\.\usbmuxd"))          # -> False
open(r"\\.\usbmuxd", "r+b")                     # probe via pinned venv python
```

Output:

```
\\.\usbmuxd exists: False
OSError: [Errno 2] No such file or directory: '\\\\.\\usbmuxd'
```

Interpretation: the classic named-pipe endpoint is absent. Note that the
pinned upstream on Windows does **not** use this pipe; it resolves usbmux to a
TCP endpoint (`pymobiledevice3.osu` `Win32.usbmux_address` →
`MuxConnection.ITUNES_HOST` = `('127.0.0.1', 27015)`, `AF_INET`), so Probe 4
is the authoritative transport check.

### Probe 4 — Authoritative upstream usbmux probe (pinned upstream, in-process)

```python
import asyncio

async def main():
    from pymobiledevice3.usbmux import list_devices
    try:
        devs = await list_devices()
        print("upstream pymobiledevice3 usbmux list_devices() OK, "
              "device count:", len(devs))
    except Exception:
        print("upstream pymobiledevice3 usbmux list_devices() FAILED:")

asyncio.run(main())
```

Run with `.venv\Scripts\python.exe` (`pymobiledevice3` 11.3.0, unmodified
upstream commit `ec4ac06a850a6a884ca778350621f354faf347c6`).

Output:

```
upstream pymobiledevice3 usbmux list_devices() OK, device count: 0
```

Interpretation: the upstream transport connects to the host's usbmux endpoint
and the mux answers, but reports **zero attached devices**. This is the same
condition the runtime's `status()` would surface as `NOT_READY` — it is valid
runtime behavior, but it is not the R3-08 completion gate.

Honesty note: the first probe attempt called `list_devices()` without awaiting
the coroutine (`TypeError: 'coroutine' object is not iterable`). That was an
API-usage error in the probe, not device evidence; it was re-run awaited, and
only the awaited result above is relied on.

succeed. With zero attached devices there is no lockdown/RSD transport and no

is impossible. Declaring R3-08 (or R3 100%) on deterministic work alone would
be a false pass. The goal is therefore **BLOCKED_R3_08**.
